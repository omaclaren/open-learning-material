15  Attention

15.1 Attention as similarity-based lookup

Returning to our colour example, we want to predict the token following wear. To form the search input for the similarity-based lookup, we construct a query vector from the embedding of wear using a learned transformation. We can think of the query as representing a question about what information would be useful for the current prediction.

Each token in the available text also supplies a key and a value, constructed from its embedding using learned transformations. The key is used for comparison with the query in the similarity-based lookup. The associated value contains information from that token which we can use for the prediction. We compare the query with each key to determine how much weight to give the corresponding value, then form a weighted average of the values.

We use vector dot products to calculate the query–key similarities. These comparisons provide scores, which we convert into weights summing to one. The available key–value entries include the current token, so we also compare the query from wear with its own key and include its value in the weighted average. This gives us a representation that draws on the history and can be used to predict the next token.

This develops the weighted-average idea from our nearest-neighbour example. After working through the calculation, we will make the connection to kernel smoothing.

15.1.1 One query and a supplied table

To understand how this combination works, we first consider a single query and a supplied table of keys and values. Here the numbers are chosen for simplicity and convenience but are otherwise arbitrary.

Suppose our query is \(q=(1,0)^T\), and our table contains two entries:

Entry Key Value
1 \(k_1=(1,0)^T\) \(v_1=(2,0)^T\)
2 \(k_2=(-1,0)^T\) \(v_2=(0,4)^T\)

The keys and the query have the same number of components so that we can take their dot products.

First, we calculate a comparison score for each key:

\[ s_j=q^T k_j. \]

For these vectors, \(s_1=1\) and \(s_2=-1\). A dot product depends on both the lengths of the vectors and how they are aligned. Here the two keys have equal length, and the query points in the same direction as the first key and the opposite direction to the second.

We want larger scores to give larger weights, with non-negative weights that sum to one. A standard way to do this is the softmax operation:

\[ a_j=\frac{\exp(s_j)}{\sum_\ell\exp(s_\ell)}. \]

Exponentiating gives positive numbers, and dividing by their sum makes the weights sum to one. In this example,

\[ a_1=\frac{e^1}{e^1+e^{-1}}\approx0.881, \qquad a_2=\frac{e^{-1}}{e^1+e^{-1}}\approx0.119. \]

Finally, we form the weighted average of the values, which we denote by \(z\):

\[ z=a_1v_1+a_2v_2 \approx0.881\begin{pmatrix}2\\0\end{pmatrix} +0.119\begin{pmatrix}0\\4\end{pmatrix} \approx\begin{pmatrix}1.762\\0.477\end{pmatrix}. \]

15.1.2 The calculation in code

We can carry out the same calculation using PyTorch tensors. Each row of keys is a key vector, and the matching row of values contains its associated value:

import torch

query = torch.tensor([1.0, 0.0])
keys = torch.tensor([[1.0, 0.0], [-1.0, 0.0]])
values = torch.tensor([[2.0, 0.0], [0.0, 4.0]])

# One dot product for each key.
scores = keys @ query

# Softmax: exponentiate, then divide by the sum.
weights = torch.exp(scores)
weights = weights / weights.sum()

# Show the contribution from each value explicitly.
z = weights[0] * values[0] + weights[1] * values[1]

print(scores)
print(weights)
print(z)

This gives

tensor([ 1., -1.])
tensor([0.8808, 0.1192])
tensor([1.7616, 0.4768])

The matrix–vector product keys @ query calculates the dot product of each key row with the query. Once we have checked the individual contributions, we can also write the last calculation as z = weights @ values.

If we change the query to \((0,0)^T\), both scores become zero. The weights are then \(1/2\) and \(1/2\), giving the ordinary average \(z=(1,2)^T\). If we instead use \(q=(-1,0)^T\), the weights reverse, and the second value makes the larger contribution. The table has stayed fixed; the combination changes with the query.

We can also change a value without changing its key. For example, replacing \(v_1\) by \((3,2)^T\) leaves the scores and weights unchanged for our original query, but changes the resulting \(z\). This separates the information used for the comparison from the information we combine.

15.1.3 Connection to nearest neighbours and smoothing

This has the same basic structure as our original nearest-neighbour example: compare a new input with the stored inputs, then combine the associated outputs. Rather than taking one or two nearest entries, we have given each entry a weight determined by its comparison with the query.

In kernel smoothing, a non-negative function measures how strongly a stored input should contribute at a query location. We normalise these weights and combine the corresponding values. Our calculation has this form, using \(\exp(q^T k_j)\) as the weighting function. The word smoothing describes the weighted-average calculation here; the entries need not be nearby times or neighbouring words.

There is an important difference when we use this calculation within a language model. In nearest-neighbour regression, the values were observed outputs and their average was our prediction. In attention, the values carry information from the supplied text, and their average is a representation used for the prediction. We still need a further calculation to turn that representation into probabilities for the next token.
